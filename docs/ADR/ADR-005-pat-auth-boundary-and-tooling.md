# ADR-005: PAT Authentication Boundary and Tooling

Status: Accepted  
Date: 2026-04-09

Upstream `pass-cli` `1.10.0` adds personal access token (PAT) login (`pass-cli login --personal-access-token` or `PROTON_PASS_PERSONAL_ACCESS_TOKEN=... pass-cli login`) plus a new `pat` / `personal-access-token` management namespace. This invalidates the older project assumption that `pass-cli` authentication only meant web or interactive user-account login. Decision: keep session establishment (`login`, `logout`) out of band even when the session is PAT-backed, because the MCP server still delegates authentication to `pass-cli` and should not collect or broker credentials. Separately, treat PAT administration as a vault-adjacent management surface rather than login lifecycle: metadata/admin operations such as list, delete, access grant/revoke, and access inspection are in-domain candidates for future MCP tools, while secret-emitting operations (`pat create`, `pat renew`) remain deferred because they mint bearer credentials that are shown exactly once and would be exposed to normal MCP tool transcripts and model context. No PAT resources will be added for now because PAT state is both dynamic and security-sensitive. This recommendation relies in part on an inference from upstream docs: PATs appear to be provisioned from an already-authenticated account session and then used for later scoped logins, rather than replacing the need for an initial trusted bootstrap flow.
